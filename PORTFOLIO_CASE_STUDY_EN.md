# Enterprise Data Warehouse Blueprint + ETL Proof
### SQL Server · Star Schema · Power BI Report Server — on-premise, no cloud

**Project 05 · delivered 2026-11-26 · Persian (RTL) enterprise BI engagement**

---

## 1. The brief (and what was actually provable)

An organization running everything inside its own network wants to turn operational systems
into a star-schema data warehouse, monitor data quality through a reject path, and publish
reports on an **internal Power BI Report Server — no cloud**.

The attached statement of work was **not available** and no SQL Server / Report Server
instance was provided. The engagement was therefore scoped to what could be *proven*:

| Deliverable layer | What was produced |
|---|---|
| Model design | Complete, idempotent **T-SQL DDL** (staging → reject → dimensions/facts) with Persian (Jalali) calendar keys, CHECK constraints, FKs, indexes |
| ETL logic | A **real, executed** Python ETL over intentionally dirty staging data, with logging, reject path and post-load quality controls |
| Semantic layer | DAX measure library (revenue, margin, returns, Jalali YTD/MTD, MoM/YoY, region rank/share, ABC, reject rate) |
| Deployment | Architecture, security/RLS design, and a role-by-role installation checklist |
| Demo | A 5-page Persian RTL Streamlit app whose "live ETL" page really executes the pipeline |

**What is explicitly *not* claimed:** SQL Server installation, Report Server
installation/licensing, report publication, RLS enforcement, SSL, load testing, UAT,
or any ROI/efficiency benefit. See `LIMITATIONS.md` (21 numbered limits).

## 2. Data — synthetic, reproducible, disclosed everywhere

No public or client dataset exists for this scenario. All data is generated by
`scripts/generate_all_data.py` with **`seed=14030505`**, currency **IRR (ریال)**,
calendar **Jalali 1403**:

| Table | Rows | Notes |
|---|---:|---|
| `dim_date` | 366 | Jalali year 1403 + Gregorian equivalents, quarter, weekday, Friday flag |
| `dim_region` | 12 | geographic zones |
| `dim_customer` | 500 | B2C/B2B, three sales channels, region FK |
| `dim_product` | 80 | 6 categories, list price and unit cost |
| `fact_sales` | 30,000 | one row per sales line; `net = qty × price × (1 − discount)` |
| `fact_returns` | 2,000 | references `sale_id`, quantity and amount bounded by the source line |
| `stg_sales_raw` | 300 | **deliberately dirty**: 4 date formats, thousands separators, padded strings, blank discount |

Price levels are calibrated with a single `PRICE_SCALE` knob so the demo reaches an
enterprise-like "hemt" (۱۰¹² IRR) scale — that is scale realism, **not** a market estimate.

## 3. The pipeline — actually run, not described

```text
stg_sales_raw.csv (300 rows, dirty)
  → [1/4] dimensions loaded  → dim_date=366 | dim_region=12 | dim_product=80 | dim_customer=500
  → [2/4] facts loaded       → fact_sales=30,000 | fact_returns=2,000
  → [3/4] cleaned            → read 300 | clean 300 | reject 0
  → [4/4] quality controls   → orphan FKs = 0 · net recalculation mismatch = 0 · distinct regions = 12
  → Σ net_amount_irr = 12,491,123,417,390 IRR
  → status SUCCESS · output model/dw_demo.sqlite
```

Normalization rules implemented and unit-tested:

* **Date**: `1403/12/12` (Jalali) · `2024/07/17` · `28-07-2024` · `2024-07-28` → integer Jalali `date_key`
* **Amounts**: strip thousands separators (`,` `٬` `,` and spaces), reject non-numeric
* **Strings**: trim; **blank discount → 0**; support `5%` / `۵٪` as well as `0.05`
* **Lookups**: unknown region/date → routed to `dw.etl_reject` with stage, reason and raw JSON payload

In this sample every row is convertible, so **reject count is 0**. The reject path is code-complete
and proven separately by tests that feed invalid dates/amounts — not by production failures.

`dw_demo.sqlite` is a **local stand-in for SQL Server**, stated in the app, in the ETL banner,
in `VALIDATION.md` and `LIMITATIONS.md`.

## 4. Model

Star schema, conformed dimensions, transaction facts. Date key is the Jalali `YYYYMMDD`
integer; `jalali_date_key` mirrors it so DAX time-intelligence works on a Persian calendar
while `gregorian_date` keeps the model compatible with standard date functions.

```text
dim_date ─┐
dim_region ┴─ dim_customer ─┐
dim_product ───────────────-┼──▶ fact_sales ──▶ fact_returns
                            └──▶ (region denormalized into the fact for report speed)
```

Design decisions and their costs are tabulated in `model/MODEL.md` §8 — including why Import
mode, why the region is denormalized into the fact, and why rejects live in a table rather
than a file.

## 5. Security (designed, documented, not enforced)

Region-level RLS ("a regional manager sees only their region") is designed around a
`DimUserRegion(user_principal, region_id)` mapping plus a DAX filter
`[region_id] = LOOKUPVALUE(...)`.

**Status: documentation only.** No security policy was created, no `.pbix` exists, and
`View as` was never run. This is called out in the app, in `ARCHITECTURE.md` and as
limitation L12.

## 6. The demo app

`streamlit run app.py --server.port 8506` — five Persian/RTL pages, Vazirmatn, Jalali dates,
IRR formatting, graphite `#232b36` + red `#d64541` on `#f6f7f8`:

1. **Warehouse overview** — KPIs, architecture strip, star-schema diagram, and three explicit
   "this project does not claim" cards.
2. **Live ETL pipeline** — dirty-row viewer plus a button that *really* shells out to
   `model/etl_staging_to_dw.py`; the raw console log and the resulting SQLite table counts are shown.
3. **Sample sales analysis** — region filter, Jalali monthly trend, regional revenue, category mix,
   return reasons, top-10 products. Charts are forced `direction: ltr` so Persian labels never
   render half-clipped; bar labels use `cliponaxis=False`.
4. **Deployment & architecture** — target architecture, honest component status matrix,
   installation steps with owners, technical trade-offs.
5. **About the data** — seed, executed quality controls, limitations, sources.

## 7. Verification

```text
$ python3 -m unittest discover -s tests
Ran 37 tests — OK
```

Coverage: key uniqueness, FK integrity in both directions, amount recalculation
(`net`, `gross`, `cost`), region consistency between fact and customer, return ≤ sale line,
all four date formats, thousands-separator stripping, blank-discount rule, artifact presence,
theme JSON validity, SVG well-formedness, and a locked total-revenue assertion so a seed or
logic drift fails loudly.

Streamlit `AppTest` ran all five pages with zero exceptions and zero warnings; the ETL button
was clicked programmatically and returned the real script log.

## 9. Honest one-paragraph summary

This portfolio piece demonstrates a defensible **design** for an on-premise Persian data
warehouse and a **working ETL proof** that transforms messy staging data into a consistent
star schema with verified totals. It deliberately does *not* simulate an installation: no
server was configured, no report was published, no row-level security was enforced, and the
numbers are reproducible synthetic samples. What a reviewer can verify today is the DDL, the
executed pipeline and its logs, the test suite, and the deployment plan — plus a clear list of
exactly what remains unproven.
