# معماری راهکار (ARCHITECTURE.md)

> **وضعیت صداقت:** این یک *طرح معماری* است. SQL Server نصب نشده، Power BI Report Server نصب یا
> لایسنس نشده و هیچ گزارش سازمانی منتشر نشده است. اثبات کار: DDL کامل در `model/schema.sql`،
> ETL اجراشده در `model/etl_staging_to_dw.py` (خروجی `model/dw_demo.sqlite`) و اسناد استقرار.

## ۱) معماری هدف (بدون ابر)

```text
┌──────────────── شبکهٔ داخلی سازمان (on‑prem) ──────────────────────────────┐
│                                                                           │
│  سیستم‌های عملیاتی                     SQL Server (DW)                    │
│  ├─ ERP فروش      ──┐                  ┌──────────────────────────────┐    │
│  ├─ CRM           ──┼─ استخراج ──────▶ │ stg.sales_raw                │    │
│  └─ انبار/مرجوعی  ──┘   (فایل/CDC)     │   ↓ پاک‌سازی (SSIS یا Python) │    │
│                                        │ dw.etl_reject  (پایش کیفیت)  │    │
│                                        │ dw.dim_* / dw.fact_*         │    │
│                                        │ dw.etl_load_log / batch_ctrl │    │
│                                        └──────────────┬───────────────┘    │
│                                                       │ Import mode        │
│                                        ┌──────────────▼───────────────┐    │
│  کاربران گزارش  ◀── HTTPS/AD ────────  │ Power BI Report Server       │    │
│  (مرورگر / Excel / موبایل)             │  ├─ Report Portal            │    │
│                                        │  ├─ Report Server DB (SQL)   │    │
│                                        │  └─ Scheduled Refresh        │    │
│                                        └──────────────────────────────┘    │
└───────────────────────────────────────────────────────────────────────────┘
        هیچ مؤلفه‌ای بیرون از شبکه لازم نیست؛ بدون Azure/Fabric/Power BI Service.
```

## ۲) لایه‌ها و مسئولیت‌ها

| لایه | مؤلفه | مسئول (پیشنهاد) | خروجی |
|---|---|---|---|
| منبع | ERP، CRM، سیستم مرجوعی | تیم کاربرد | فایل/جدول استخراج |
| Staging | `stg.sales_raw` (SQL Server) | تیم داده | دادهٔ خام با `load_batch_id` |
| پاک‌سازی | SSIS Package یا `etl_staging_to_dw.py` | تیم داده | `dw.stg_sales_cleaned` + Reject |
| انبار | `dw.dim_*`, `dw.fact_*` | DBA + تیم داده | استاراسکیما با ایندکس/FK |
| معنایی | Dataset در Power BI Desktop (`.pbix`) | تحلیلگر BI | سنجه‌های DAX |
| ارائه | Power BI Report Server | تیم BI/زیرساخت | گزارش RTL، Refresh زمان‌بندی‌شده |

## ۳) جریان داده و کیفیت

1. **استخراج** فایل روزانه در پوشهٔ امن؛ محاسبهٔ `SHA-256` و ثبت در `dw.etl_batch_control`
   (ضد بارِ دوباره‌شماری).
2. **بار staging** با `TRUNCATE` و `BULK INSERT`؛ ثبت تعداد ردیف در `dw.etl_load_log`.
3. **پاک‌سازی** با قاعده‌های ثابت:
   * تاریخ: `1403/12/12` (شمسی) ، `2024/07/17` (میلادی) ، `28-07-2024` ، `2024-07-28` → `date_key`
   * مبالغ: حذف `,`/فاصلهٔ هزارگان؛ منفی/صفر غیرمجاز
   * رشته‌ها: `TRIM`؛ تخفیف خالی → `0`
   * جست‌وجوی ابعاد: منطقه/کالا/مشتری ناموجود → Reject
4. **Reject** در `dw.etl_reject` با `reject_stage` و `raw_payload`؛ داشبورد کیفیت روی همین جدول.
5. **بار فکت/ابعاد** در یک تراکنش؛ در صورت خطا `ROLLBACK` و وضعیت `FAILED`.
6. **بازآموزی تجمعی**: `SUM(net_amount_irr)` با منبع مقایسه می‌شود (کنترل توازن).

## ۴) امنیت و RLS

| موضوع | طراحی | وضعیت در این پروژه |
|---|---|---|
| احراز هویت | Windows Auth / AD گروه‌ها | مستند — تست نشده |
| RLS «مدیر منطقه فقط منطقهٔ خود» | جدول نگاشت `DimUserRegion(UserPrincipal, region_id)` + فیلتر `[region_id] = LOOKUPVALUE(...)` | **فقط مستند** — بدون Security Policy، بدون View-as |
| دسترسی اشیاء | نقش `dw_reader` (SELECT)، `dw_etl` (نوشتن) | مستند |
| انتقال | HTTPS با گواهی داخلی (CA سازمان) | مستند — SSL تست نشده |
| داده حساس | مثال: ستون‌های هویتی/تماس حذف یا ماسک | در نمونه چنین ستونی وجود ندارد |

نمونهٔ فیلتر RLS برای تغییر آینده (اجرا نشده):

```dax
// نقش «مدیر منطقه» — روی dim_region یا fact_sales
VAR u = USERPRINCIPALNAME()
VAR r = LOOKUPVALUE ( DimUserRegion[region_id], DimUserRegion[user_principal], u )
RETURN fact_sales[region_id] = r
```

## ۵) کارایی (فقط آنچه در سرور واقعی معنا دارد)

* فکت‌ها `CLUSTERED` روی کلید طبیعی؛ ایندکس `NONCLUSTERED` روی `date_key`,`region_id`.
* در حجم‌های بالاتر: **Columnstore** روی `fact_sales`، **پارتیشن‌بندی** ماهانه شمسی،
  **آمار** به‌روز و `OPTION (RECOMPILE)` برای کوئری‌های پارامتری.
* در Power BI: Import mode + Aggregation برای گزارش‌های سنگین؛ DirectQuery فقط اگر الزام
  نزدیک‌به‌زمان‌واقعی باشد (توصیه نمی‌شود).
* این موارد در SQLite دمو **قابل سنجش نیستند** و ادعای کارایی نمی‌شود.

## ۶) RTO/RPO و نگهداشت

| موضوع | پیشنهاد |
|---|---|
| بکاپ DW | Full روزانه + Diff هر ۴ ساعت (به تصمیم DBA) |
| RPO هدف | ≤ ۴ ساعت برای DW، ≤ ۲۴ ساعت برای گزارش‌ها |
| RTO هدف | ≤ ۸ ساعت (بازگردانی + Refresh گزارش) |
| نگهداشت Reject | ۹۰ روز سپس آرشیو |
| نسخه‌بندی DDL | همین مخزن؛ تغییر با PR و Review توسط DBA |

اعداد RTO/RPO **پیشنهاد** هستند و با سازمان توافق نشده‌اند.
